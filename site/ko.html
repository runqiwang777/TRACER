TRACER는 언어 모델과 수학 증명 검사기 Lean을 연결합니다. 오류 정보와 관련 예제를 모델에 제공하고, 수정한 증명을 다시 검사합니다.

TRACER가 하는 일

대상 프로젝트의 검사기를 통과한 수정만 성공으로 기록합니다.

01

증명 후보 검사

명제와 의존성을 고정하고 제안된 증명을 컴파일합니다.

02

오류 정리

원문을 보존하고, 찾을 수 없는 이름과 타입 차이 및 남은 목표를 근거와 함께 추출합니다.

03

수정 시도

피드백과 설정에 따른 관련 예제를 제공합니다. 시도 횟수에는 상한이 있습니다.

04

근거 저장

후보, 오류, 사용량 및 성공한 증명을 저장해 독립적인 재검증을 지원합니다.

완료한 연구에서 확인한 결과

서로 다른 24문제를 두 모델 설정과 여러 조건에서 반복하여 864개의 작업 실행을 얻었습니다. 서로 다른 정리 864개를 뜻하지 않습니다.

첫 번째 시도735/864 · 85.1%
최대 세 번의 시도811/864 · 93.9%

첫 시도에서 실패한 작업 중 76개가 이후 시도에서 추가로 성공했습니다.

85.1%에서 93.9%로의 변화에는 재시도 효과도 포함됩니다. 전부 피드백의 효과로 해석할 수 없습니다.

모델은 오류 메시지의 의미를 활용했을까요, 아니면 한 번 더 시도해서 성공했을까요?

오류 없이 다시 시도하는 조건과 비교하면 Flash의 성공 수는 같고 Pro는 2개 적었습니다. 조건마다 72개 작업입니다. 피드백의 안정적인 우위는 아직 확인되지 않았습니다.

방법과 근거의 범위

Lean 통과는 주어진 환경과 가정 아래에서의 형식적 유효성을 뜻합니다. AI 보조 검토는 완전한 사람의 수학적 심사가 아닙니다. 오프라인 안전 테스트와 한 차례 Linux 컨테이너 실행도 범용 샌드박스를 보장하지 않습니다.

같은 실패에서 비교

동일한 실패 증명을 재사용하고 다음 시도에 제공하는 정보만 바꿉니다.

정보가 쓰였는지 확인

추출 항목을 원문과 연결하고 수정이 해당 오류와 관련 있는지 살펴봅니다.

실제 유지보수 작업 평가

여러 프로젝트의 수정 이력에서 문제를 만들고, 참조 정답을 생성 과정과 분리합니다.

어려운 점

이름 누락, 타입 불일치, 미해결 목표, 의존성 변경은 서로 다른 실패를 만듭니다. 필요한 문맥 보존, 정답 유출 방지, API 장애 구분, 실제 시간과 토큰 비용 측정이 필요합니다.

완료한 일, 진행 중인 일, 계획

완료

횟수가 제한된 수정, 근거가 연결된 진단, 예제 검색, 증명 저장, 재현 가능한 실패 24개, 5개 프로젝트의 과거 수정에서 만든 테스트 254문제.

진행 중

DeepSeek, GLM, MiniMax를 사용하는 비교 연구입니다. 최종 결과는 전체 기록 감사와 독립 재컴파일 후 공개합니다. 이 페이지는 실시간 실행 모니터가 아닙니다.

계획

진단의 사실 하나만 바꿔 코드 수정에 미치는 영향을 검사합니다. 이후 오류에 따른 피드백 선택을 독립 데이터에서 평가합니다.
